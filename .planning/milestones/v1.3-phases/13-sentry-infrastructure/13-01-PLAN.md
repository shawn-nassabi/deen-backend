Exact content (per PATTERNS.md Pattern 2 and RESEARCH.md Pattern 2):

```python
import uuid

from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request

from core.context import correlation_id


class CorrelationIdMiddleware(BaseHTTPMiddleware):
    """Generate a fresh UUID per request and propagate it via ContextVar.

    D-03: Always generates server-side UUID. Incoming X-Correlation-ID header
    from clients is ignored — never trusted as a source of truth.
    """

    async def dispatch(self, request: Request, call_next):
        cid = str(uuid.uuid4())
        correlation_id.set(cid)
        response = await call_next(request)
        response.headers["X-Correlation-ID"] = cid
        return response
```

Key constraints:
- Import `Request` from `starlette.requests` (not `fastapi`), as this is a Starlette middleware class.
- `str(uuid.uuid4())` produces the canonical lowercase-hyphenated UUID string format.
- `correlation_id.set(cid)` MUST be called BEFORE `await call_next(request)` — this sets the ContextVar in the current async context so all downstream coroutines inherit it.
- `response.headers["X-Correlation-ID"] = cid` MUST be called AFTER `call_next` returns, when the response object exists.
- Do NOT read the incoming `X-Correlation-ID` header — D-03 requires server-generated only.
  </action>

Exact content (per D-04, D-05, D-06, D-07 CORRECTED, D-08, D-09 and PATTERNS.md Pattern 3):

```python
import logging
import os

import sentry_sdk
from sentry_sdk.integrations.logging import LoggingIntegration

from core.config import SENTRY_DSN

# D-05: Both SENTRY_ENABLED=true AND SENTRY_DSN must be set for Sentry to activate.
# Absence of either leaves Sentry completely silent — safe for local dev.
SENTRY_ENABLED: bool = os.getenv("SENTRY_ENABLED", "").lower() == "true"


def _scrub_pii(event: dict, hint: dict) -> dict:
    """Remove request body from Sentry error events.

    D-08: Drops event["request"]["data"] entirely — the most defensive
    approach for GDPR Article 9 special-category data (Islamic religious content).
    Stack traces and tags are preserved; only the request body is removed.

    Note (D-09): before_send applies to error/exception events only.
    Sentry Logs use a separate delivery path — Phases 14-16 control
    log PII by not including user_query in extra={} fields.
    """
    if "request" in event:
        event["request"].pop("data", None)
    return event


if SENTRY_ENABLED and SENTRY_DSN:
    sentry_sdk.init(
        dsn=SENTRY_DSN,
        send_default_pii=False,
        environment=os.getenv("ENV", "development"),
        integrations=[
            # FastApiIntegration and StarletteIntegration are auto-enabled by sentry-sdk[fastapi].
            # LoggingIntegration must be listed explicitly — it is NOT auto-enabled.
            LoggingIntegration(
                level=logging.INFO,           # breadcrumbs threshold
                event_level=logging.ERROR,    # error event threshold
                sentry_logs_level=logging.INFO,  # Sentry Logs threshold (valid at 2.27.0)
            )
        ],
        before_send=_scrub_pii,
        # _experiments required at sentry-sdk 2.27.0 — top-level enable_logs only valid at >= 2.35.0
        _experiments={"enable_logs": True},
    )


def bind_sentry_scope(
    cid: str,
    endpoint: str,
    session_id: str | None = None,
    user_id: str | None = None,
) -> None:
    """Set per-request Sentry tags on the current isolation scope.

    No-op when SENTRY_ENABLED is False. Route handlers in Phase 14+ call
    this after extracting session_id and user_id from the request context.

    D-07 CORRECTED: Uses get_isolation_scope().set_tag() — sentry_sdk.configure_scope()
    is deprecated at 2.27.0 and emits DeprecationWarning on every call.
    FastApiIntegration (auto-enabled) creates a fresh isolation_scope per request
    via SentryAsgiMiddleware, so set_tag() correctly targets the per-request scope.
    """
    if not SENTRY_ENABLED:
        return
    scope = sentry_sdk.get_isolation_scope()
    scope.set_tag("correlation_id", cid)
    scope.set_tag("endpoint", endpoint)
    if session_id:
        scope.set_tag("session_id", session_id)
    if user_id:
        scope.set_tag("user_id", user_id)
```

Critical implementation constraints:
- `SENTRY_ENABLED` defined BEFORE the `if SENTRY_ENABLED and SENTRY_DSN:` block — it is used both as an init gate and exported for `catch_exceptions_mw` in `main.py`.
- `from core.config import SENTRY_DSN` — import from the existing config module, NOT `os.getenv("SENTRY_DSN")` directly.
- Do NOT add `FastApiIntegration` or `StarletteIntegration` to the `integrations=[]` list — they are auto-enabled by `sentry-sdk[fastapi]` and adding them explicitly causes duplicate registration.
- `send_default_pii=False` — replaces the current `True` in main.py. Required for GDPR Article 9 compliance.
- `_experiments={"enable_logs": True}` stays inside `_experiments` dict — NOT a top-level param at 2.27.0.
- `bind_sentry_scope` uses `sentry_sdk.get_isolation_scope()` — NOT the deprecated `configure_scope()`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → CorrelationIdMiddleware | Untrusted client could send arbitrary X-Correlation-ID header |
| Sentry SDK → Sentry remote | Error event payload crosses to external service; may contain PII from request body |
| env vars → core/sentry.py | SENTRY_ENABLED and SENTRY_DSN loaded from environment at module import time |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-01 | Tampering | CorrelationIdMiddleware | mitigate | D-03: always generate server-side UUID via `str(uuid.uuid4())` — incoming `X-Correlation-ID` header from clients is never read. `grep -c "request.headers" core/middleware.py` must return `0`. |
| T-13-02 | Information Disclosure | _scrub_pii / before_send | mitigate | D-08: `event["request"].pop("data", None)` removes entire request body (including `user_query`) before Sentry transport. `grep -c ".pop..data" core/sentry.py` must return `1`. GDPR Article 9 compliance for Islamic religious content. |
| T-13-03 | Information Disclosure | SENTRY_DSN in env | accept | SENTRY_DSN loaded from `.env` via `core/config.py`; never hardcoded or logged. Risk: DSN exposure in process listing — low risk, standard practice for all SaaS SDKs. `.env` is gitignored. |
| T-13-04 | Information Disclosure | Sentry Logs path (INFO+) | accept | D-09 documents that `before_send` does NOT cover Sentry Logs (requires `before_send_log` at sentry-sdk >= 2.35.0). Mitigation deferred: Phases 14-16 must not put `user_query` content into `extra={}` fields. Risk accepted at Phase 13 level — no log calls added here. |
| T-13-05 | Denial of Service | sentry_sdk.init() | mitigate | Python module caching (`sys.modules`) guarantees the `if SENTRY_ENABLED and SENTRY_DSN:` block executes exactly once per process. No additional `is_initialized()` guard needed. Double-import cannot cause duplicate Sentry sessions. |
| T-13-06 | Information Disclosure | SENTRY_ENABLED in dev | mitigate | D-05: `SENTRY_ENABLED` defaults to `False` (requires explicit `SENTRY_ENABLED=true` in env). Local dev with no `.env` setting never triggers Sentry connections. INFRA-01 requirement. |
</threat_model>
