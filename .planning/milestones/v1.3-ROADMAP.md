# Milestone v1.3: Sentry Deep Integration

**Status:** ✅ SHIPPED 2026-04-28
**Phases:** 13–16
**Total Plans:** 8

## Overview

Pure observability pass: instrumented all main API endpoints, the core LangGraph pipeline, agent tools, and the FAIR-RAG sub-graph with structured `extra={}` logging flowing to Sentry. Every log call carries `correlation_id`. WARNING boundaries added at all silent failure paths. Production-only, opt-in via `SENTRY_ENABLED=true`.

No API surface changes. No LangGraph topology changes. No new database tables.

## Phases

### Phase 13: Sentry Infrastructure

**Goal**: Sentry is initialized safely — active only in production when explicitly enabled, with PII scrubbed and every request carrying a traceable correlation_id
**Depends on**: Nothing (infrastructure foundation — all other v1.3 phases depend on this)
**Requirements**: INFRA-01, INFRA-02, INFRA-03, INFRA-04, INFRA-05
**Plans**: 2 plans

Plans:
- [x] 13-01-PLAN.md — Create core/context.py, core/middleware.py, core/sentry.py (new infrastructure modules)
- [x] 13-02-PLAN.md — Wire new modules into main.py (replace sentry init, register middleware, refactor catch_exceptions_mw)

**Details:**

Success Criteria (all met):
1. Running the server locally with `SENTRY_ENABLED` unset (or `false`) produces zero outbound connections to Sentry
2. Setting `SENTRY_ENABLED=true` AND a valid `SENTRY_DSN` causes `sentry_sdk.init()` to execute exactly once at startup with `LoggingIntegration(level=INFO, event_level=ERROR)` configured
3. Every HTTP response carries an `X-Correlation-ID` header; all log events from that request include it
4. A Sentry event captured during a request includes `session_id`, `user_id` (if authenticated), `endpoint`, and `correlation_id` as tags
5. A test request containing `user_query` in the body does not expose that text in any Sentry event payload (`before_send` hook strips it)

Key decisions:
- Side-effect import (`import core.sentry`) keeps main.py clean; Python `sys.modules` caching guarantees single init
- `FastApiIntegration` excluded from integrations list — `sentry-sdk[fastapi]` auto-enables it; explicit inclusion causes duplicate setup
- Never read incoming `X-Correlation-ID` header — generates server-side UUID only (D-03 threat mitigation)

### Phase 16: Fiqh Sub-graph Instrumentation

**Goal**: The FAIR-RAG loop emits structured, searchable warnings at every meaningful failure boundary — zero-doc retrievals, total evidence loss, and iteration exhaustion are all visible in Sentry
**Depends on**: Phase 13
**Requirements**: FIQH-01, FIQH-02, FIQH-03, FIQH-04
**Plans**: 1 plan

Plans:
- [x] 16-01-PLAN.md — Instrument agents/fiqh/fiqh_graph.py (convert 10 existing log calls to extra={} style, add 3 WARNING boundaries) and create tests/test_fiqh_graph_logging.py (7 unit tests for WARNING boundaries)

**Details:**

Success Criteria (all met):
1. All existing log calls in `agents/fiqh/fiqh_graph.py` use `extra={}` with `iteration`, `verdict`, and `doc_count` as top-level keys — Sentry Logs search for `iteration:2` returns matching events
2. Running a fiqh query that results in zero retrieved documents on any iteration produces a WARNING log — visible in Sentry Logs with the iteration number
3. A scenario where the evidence filter removes all accumulated documents produces a WARNING log with `doc_count=0` before the fail-open path executes
4. Exhausting all 3 FAIR-RAG iterations with an INSUFFICIENT verdict produces a WARNING log containing `verdict:INSUFFICIENT` and `iteration:3` as structured fields

Key decisions:
- `current_query[:60]` dropped from `_retrieve_node` INFO log — sub-queries carry same Islamic content PII risk as original user query (D-06)
- FIQH-03 WARNING only inside `try` block — the `except`-clause fail-open path gets an ERROR log (D-08)
- FIQH-04 WARNING guarded by `state["verdict"] != "SUFFICIENT"` — prevents false-positive when SUFFICIENT is reached on the 3rd iteration exactly (D-09)

## Milestone Summary

**Timeline:** 2026-04-26 → 2026-04-28 (3 days)
**Files changed:** 64 files (+10,017 / -217 lines)

**Key Decisions:**

- Side-effect import pattern for Sentry init — module-level init fires once at import time via Python's `sys.modules` caching
- `logger.error(exc_info=True)` over `capture_exception()` — LoggingIntegration auto-captures ERROR log events; calling both creates duplicate Sentry events
- Never read incoming `X-Correlation-ID` header — clients could inject forged IDs to manipulate Sentry trace correlation (D-03)
- `FastApiIntegration` excluded from integrations list — `sentry-sdk[fastapi]` auto-enables it; explicit inclusion causes duplicate setup
- `sentry-sdk` pinned at 2.27.0 — `_experiments.enable_logs` stays in `_experiments` (top-level only valid at >= 2.35.0)
- `send_default_pii=True` must NOT be set — `before_send` hook required for GDPR Article 9 compliance (Islamic religious content = special-category data)

**Issues Resolved:**

- REF-02 data-leak bug: `/references` was returning raw exception string in HTTP 500 detail — fixed in 14-01
- All `print()` calls removed from entire codebase (api/, core/, agents/)
- All `traceback.import` + `traceback.print_exc()` patterns eliminated

**Issues Deferred:**

- Live Claude API smoke test (POST /chat/stream/agentic with real ANTHROPIC_API_KEY) in CI — runtime environment, not a code gap
- Sentry Performance tracing (custom spans for retrieval, LLM generation, fiqh iterations) — deferred to future milestone
- `before_send_log` hook for fine-grained Sentry log quota throttling — requires sentry-sdk >= 2.35.0 (current pin is 2.27.0)
- LLM token counts in log context (input/output tokens per Claude call)

**Technical Debt Incurred:**

- `ExtraFormatter` ANSI colorization not disabled for non-development environments — potential level-field corruption in Sentry if colorized escape codes are transmitted
- Phase 13-01 SUMMARY.md missing `requirements-completed` frontmatter field (documentation only, INFRA-01..05 are complete)
