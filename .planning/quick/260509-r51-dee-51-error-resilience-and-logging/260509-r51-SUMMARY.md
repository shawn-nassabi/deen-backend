# DEE-51 chatbot error resilience + observability — Summary

## Why

Production users intermittently saw "I apologize, but I'm having trouble responding right now. Please try again in a moment." with no Sentry trace. Investigation showed two root causes:

1. **Silent failure paths** — Pinecone retrieval errors and several LLM error sites used `print()` or `logger.warning(...)`, both of which bypass Sentry's `event_level=logging.ERROR` filter (`core/sentry.py:38-42`). The next incident produced no observability artifact.
2. **Zero application-level retries** — `ChatAnthropic` constructors fell back to langchain-anthropic's `max_retries=2` default with no app timeout; Pinecone async retrieval had no retry layer at all. A single transient `overloaded_error` (529), 503, 429, or network blip would surface as the SSE error event.

## What changed

### New shared module (commit `38390ea`)
- `core/resilience.py` — exposes `anthropic_retry` and `pinecone_retry` async decorators built on tenacity. Policy: 3 attempts, exponential jitter (0.5s → 8s max), `before_sleep` hook logs at WARN with attempt + next-wait. Retries only on transient classes (5xx/529/429/connection/timeout for Anthropic; ServiceException + 5xx PineconeApiException + OSError/TimeoutError for Pinecone). Auth/permission/4xx-not-429 errors surface immediately so configuration mistakes aren't masked.

### LLM client config (commit `22e9600`)
- `core/chat_models.py` — every `ChatAnthropic` constructor (generator, enhancer, classifier, translator) now passes `max_retries=5` and `timeout=60`. The ChatAnthropic-level retry sits underneath the application-level `anthropic_retry`, giving the request two independent retry layers.

### Anthropic retry coverage (commits `d4eb7a9`, `afb7401`)
Every `.ainvoke` call site on the agentic hot path now carries `@anthropic_retry` (streaming `.astream` deliberately not wrapped — partial-token retries would emit duplicate output to the SSE consumer):
- `agents/core/chat_agent.py` — `_agent_node`, `_generate_response_node`, `_check_early_exit_node` (UNETHICAL rejection), `_generate_fiqh_response_node` via a module-level `_retry_ainvoke(llm, messages)` helper.
- `modules/fiqh/{sea,refiner,filter,decomposer,classifier,generator}.py` — async LLM call sites extracted into decorated inner helpers; outer functions keep graceful-degradation try/except but now log the exhausted-retry case at ERROR.
- `modules/classification/classifier.py` — `aclassify_fiqh_query`, `aclassify_non_islamic_query`.
- `modules/translation/translator.py` — `atranslate_to_english`.
- `modules/enhancement/enhancer.py` — `aenhance_query`, `aenhance_elaboration_query`.

### Pinecone retry coverage (commits `d4eb7a9`, `b78e034`)
- `modules/retrieval/retriever.py` — `_dense_search`, `_sparse_search`, and the Quran retrieval `to_thread(index.query, ...)` call.
- `modules/fiqh/retriever.py` — dense and sparse fiqh queries via decorated `_afiqh_dense_query` / `_afiqh_sparse_query` helpers.

### Sentry-visible logging (every commit)
- All `print(f"...Error...{e}")` sites on the agentic hot path replaced with `logger.error("...", exc_info=True, extra={"correlation_id": correlation_id_ctx.get()})`.
- All `logger.warning(...)` sites in `modules/fiqh/{sea,refiner,filter}.py` for actual exceptions promoted to `logger.error(..., exc_info=True)`.
- All bare `except Exception:` silent fallbacks in `modules/fiqh/{classifier,decomposer}.py` now log at ERROR before falling back.
- `core/memory.py`, `core/vectorstore.py` — startup Redis/Pinecone init errors promoted from `print()` to `logger.error(exc_info=True)`.

## How to confirm in production

After deploy, the next "trouble responding" incident should produce a Sentry event with:
- Exception class telling us which provider/error code was the actual cause
- `correlation_id` tag matching the request
- A breadcrumb history of the WARN-level retry attempts (`anthropic transient error on attempt N, retrying in Xs: ...` or the `pinecone` equivalent) that exhausted before the user-visible error fired

If incidents drop to near-zero, the retry layer is absorbing them. If they persist, the Sentry exception class will tell us where to look next (most likely candidates that retries can't help: gunicorn worker recycle / OOM, or a non-transient Anthropic 4xx).
