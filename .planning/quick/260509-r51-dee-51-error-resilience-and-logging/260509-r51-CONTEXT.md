# Quick Task 260509-r51: DEE-51 chatbot error resilience + observability — Context

## Task Boundary

Production users intermittently see the frontend fallback string "I apologize, but I'm having trouble responding right now. Please try again in a moment." Sentry has no record of these incidents. The frontend produces that string when the backend SSE stream emits an `error` event (`core/pipeline_langgraph.py:440`) or terminates abnormally. Two work streams:

1. **Observability** — close the gaps that let exceptions reach the user without reaching Sentry.
2. **Resilience** — add retry layers around Anthropic and Pinecone so transient infrastructure errors no longer surface as user-visible failures.

## Implementation Decisions

### Linear ticket convention
- Commit prefix: `DEE-51:` on every commit in this task (per project-wide cherry-pick traceability rule).

### Anthropic retries
- Add `max_retries=5` and `timeout=60` to all four `ChatAnthropic` constructors in `core/chat_models.py`. This raises the langchain-anthropic default of 2 retries and pins an explicit per-request timeout.
- Wrap **only `.ainvoke` call sites** with a tenacity retry decorator on transient Anthropic exceptions (`anthropic.APIStatusError` for 5xx/529, `anthropic.RateLimitError` for 429, `anthropic.APIConnectionError`). Do **not** wrap `.astream` — partial-token streaming retries risk emitting duplicate output to the user.

### Pinecone retries
- Wrap `_dense_search`, `_sparse_search`, and `aretrieve_quran_documents` in `modules/retrieval/retriever.py` with tenacity retries on `pinecone.PineconeApiException` and generic transient exceptions.
- Mirror the same pattern in `modules/fiqh/retriever.py` retrieval calls.
- Retry policy: 3 attempts, exponential backoff 0.5s → 2s → 8s, jitter on. Total worst-case ≈10.5s — well within the no-proxy-timeout SSE budget.

### Claude's Discretion

- Whether to add a small shared retry helper module — yes, will introduce `core/resilience.py` exposing `anthropic_retry` and `pinecone_retry` decorators so the policy is consistent and tunable in one place.
- Whether to bump gunicorn `-w 2` to `-w 4` — **deferred**. That fix isn't strictly needed if retries land; revisit if Sentry shows worker recycling after the fix is deployed.

## Specific Ideas

- Use `tenacity` (already pinned at `tenacity==9.1.2` in `requirements.txt`) — no new dependency required.
- Use the project's existing logging convention: `logger = logging.getLogger(__name__)` at module top, `logger.error("msg", exc_info=True, extra={"correlation_id": correlation_id_ctx.get(), ...})` per `core/logging_config.py`.
- Sentry's `LoggingIntegration(event_level=logging.ERROR)` (`core/sentry.py:38-42`) means every `logger.error` becomes a Sentry event automatically — no manual `sentry_sdk.capture_exception` calls needed.
